# Internationalization (i18n)

The application is a **four-locale first-class** product:

| Locale              | Code    | Autonym       |
| ------------------- | ------- | ------------- |
| English             | `en`    | English       |
| Bahasa Melayu       | `ms`    | Bahasa Melayu |
| Simplified Chinese  | `zh-CN` | 简体中文      |
| Traditional Chinese | `zh-TW` | 繁體中文      |

`en` is the source of truth for **key structure only** — all four locales carry a full translation, not a fallback layer.

## Architecture

- **Library**: `i18next` + `react-i18next` + `i18next-browser-languagedetector` (`frontend/package.json`).
- **Module**: `frontend/src/i18n/index.ts` — resources, `SUPPORTED_LOCALES`, `LOCALE_LABELS`, `intlLocale()`, and locale normalization (`zh-Hant`, `-TW`, `-HK`, `-MO` resolve to `zh-TW`; other `zh*` to `zh-CN`).
- **Locale files**: `frontend/src/i18n/locales/{en,ms,zh-CN,zh-TW}.ts`. `en.ts` exports `export type Messages = typeof en` and every other locale is typed `Messages`, so **structural parity is enforced by `tsc`** — a missing or extra key is a compile error.
- **Formatters**: `frontend/src/lib/format.ts` — `formatDate`, `formatDateTime`, `monthName`, `weekdayName`, `formatMYR`, `formatRelativeTime`, etc. All take `intlLocale()` so dates and numbers follow the active UI locale. **Never** call `toLocaleDateString('en-GB', …)` or similar pinned-locale formatters for user-facing output; use the helpers (an `// i18n-ok` marker is required for rare internal-parse exceptions).
- **Persistence**: Selected language is stored in `localStorage` under `payroll.lang` (detector `caches`), so switching survives reloads without resetting React state, routes, or filters.
- **Server errors**: Backend `AppError` literals are translated client-side via `frontend/src/i18n/serverErrorMap.ts` (maintained with `scripts/gen-server-error-map.mjs`) plus regex patterns for `format!` messages, resolved by `getErrorMessage` in `frontend/src/lib/utils.ts`. Payroll diagnostics and action items carry stable `code` + `params` maps from the backend so they translate by code rather than parsing English text.

## Key conventions

- Semantic nested keys mirroring the feature: `payroll.detail.approve`, `attendance.kiosk.title`, `auth.login.submit`.
- **Never** create language-suffixed keys (`foo.en`, `foo.ms`). One key, four values.
- Shared verbs/states live in `common.*` (`save`, `cancel`, `loading`, `noResults`). Avoid duplicating them per feature unless context genuinely changes the meaning.
- Interpolation: `{{var}}` (`escapeValue: false` — React escapes output). Every locale must supply **the same variable set** per key.
- Plurals: `_one` / `_other` suffixes (or base + `_other` when singular equals base). Malay and Chinese often keep both forms identical, but both keys must exist.
- Inline HTML: only `<strong>`-style inline markup via `<Trans>`; `t()` renders markup literally.

## Adding a user-facing string

```text
New UI text
  -> add key to en.ts (semantic namespace)
  -> add the same key to ms.ts, zh-CN.ts, zh-TW.ts (tsc errors if omitted)
  -> run: bun run test                      (src/tests/i18n.test.ts validates parity)
  -> run: node scripts/i18n-scan.mjs --ci (hardcoded-string gate)
```

`frontend/src/tests/i18n.test.ts` enforces exact key parity, non-empty values, interpolation-variable parity, plural pairing, **no English residue** (outside an allowlist of acronyms/brand names/autonyms), no CJK in `ms`, and **script purity** (Simplified-only characters rejected in `zh-TW`; Traditional-only characters rejected in `zh-CN`).

## CI gates

- `.github/workflows/ci.yml` → `frontend-lint` runs `node scripts/i18n-scan.mjs --ci` (fails on hardcoded user-facing literals; unmapped backend messages warn) alongside the Vitest suite containing `i18n.test.ts`.
- The scanner skips lines marked `// i18n-ok` — use it only for intentional literals such as admin-editable template bodies, statutory CSV headers, internal parse formats, and test fixtures.
